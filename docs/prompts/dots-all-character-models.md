## 3. 美术方向：精致、清楚、有个性的桌游手办

建议方向是**忠于角色原画的精致卡通桌游手办**：轮廓鲜明，体积完整，造型有设计，颜色干净；保留滑稽、奇怪和夸张的角色个性。不要统一变成写实人物，也不要把所有角色都套成同一张可爱脸。

参考优先级：实际取得的角色原画/卡面识别特征 → manifest中已核对的特征 → 当前二维SVG与现有模型。原画不可取得时，用已有已确认特征完成立体解释，并明确哪些背面细节是设计补全；不要伪称看过原图，也不要因为缺少背面原画就停止所有工作。已有3D模型是待改进基线，不是造型上限。

逐角色改进以下方面：

- **轮廓与比例**：先解决头身、躯干、四肢、道具和重心。正常游戏尺寸下，不靠名字也应尽量分清角色。保留原角色主色、耳朵/帽子/鼻子/角/尾巴等核心识别特征。
- **主体结构**：身体、衣物与四肢形成有意设计的结构和自然过渡。基础几何体可用于起形，但最终不能满身明显的球体交叠、悬空短棒和随意插接。机器、骰子、房屋等本来有硬边的角色保留其结构特点。
- **面部**：眼睛贴合头部曲率，视线与表情协调；嘴唇、嘴角、鼻子和面颊有正确空间关系。检查侧脸，不能浮在脸外、埋进脸内、重复长眼睛或发生闪烁。不要所有角色复用一套相同五官。
- **服装与道具**：补足领口、袖口、帽檐、鞋底、披风厚度、关键褶皱、握持关系等能在游戏中看见的细节。线条服从布料和结构；不要用满身细碎纹理掩盖比例问题。
- **完整侧背面**：尾巴、背包、头发、衣摆和道具背面有实际体积；不能只做一张正面浮雕，不能把角色插画贴到薄片上冒充模型。
- **材质**：以柔和、干净的手绘卡通/哑光手办质感为主，避免全员高亮塑料或强金属反光。需要区分皮肤、衣物、硬道具时用受控的颜色与表面变化，不靠刺眼灯光制造“精细”。

精细度优先花在轮廓、脸、手部、关键道具和可见结构上。单纯加细分、倒角、渲染分辨率或统一贴纹理，不算完成重构。

### 坐标、大小与身份

- 导出后 **+Y向上、+Z正面、脚底在Y=0**；保持 `toy_{id}` 根节点。角色根的默认位置和旋转为零、缩放为1，变换正确应用。Blender内部坐标按导出后的Three.js实际结果检查。
- 沿用每个角色现有相对体型。当前大多数角色宽、深不超过0.6，高约0.2–1.0；不能把所有角色强行做成相同身高，也不能靠统一放大来表现精细。
- 游戏自己生成玩家颜色底座和编号。**角色GLB不烘焙底座、座位号或所有者颜色**；`ToyCharacter`已经把角色放在底座顶部约0.164处，模型内不要再抬高同样距离。
- 各角色ID、URL路由、能力对应关系保持兼容。多实例必须各有独立姿态，不能因共享骨骼或材质状态互相影响。
- 野猪坐骑要实际测骑乘位置，防止骑士悬空、脚穿肚子；不能把猪永久并入骑士模型。Bite Mark正常形态与变身形态都要可切换。

### 动画与静态姿态

- 保留 `idle / move / skill / fall / recover` 这些状态的调用契约。总包动画使用 `{id}-{state}`，独立GLB使用对应状态名；以加载器实际匹配规则为准。
- 当前各包历史实现不完全一致：原版和多个扩展已有骨骼；Wurstii manifest主要登记idle/move/skill，旧文档还保留“整体弹跳”的描述。先检查实际GLB，再决定保留、重做或补齐，不要以旧文档代替检查。
- 对适合关节运动的角色，移动应有与身体结构匹配的摆臂、迈步或摆尾；无腿、轮子、多体组合等采用各自合适的运动，不硬套双足动作。idle保持克制，skill是视觉表现，不执行游戏规则。
- 外层 `Board3D` 已处理沿路线位移、传送、倒地倾角与起立。动画应留在局部，避免再次搬动世界坐标、重复整个人翻倒、脚滑到别格或放大道具遮住邻格。
- `cloneToyModel` 的减少动效路径会去掉骨骼，直接使用静态绑定几何；**新模型的静态形状必须与绑定姿态一致**。压缩/量化后也要验证，不能只检查动画开启时正常。
- 如造型确实需要更合适的骨骼数量，可以修改资源及对应检查，但不重写整个动画调度。保持同一GLB不同实例独立、静态不变形、关节有效、角色不漂移的验证。

### 材质和资源加载：这里容易踩坑

- `pawn-materials.ts` 在高画质会新建 `MeshPhysicalMaterial`，当前不会完整保留源材质贴图、法线图及PBR参数，而且会统一roughness/metalness。因此不能只在Blender里加贴图就宣布游戏材质完成。
- 优先用合理几何、顶点色和共享调色板实现效果。确实需要贴图时，最小化修改材质转换，使高低画质都正确保留所需通道，并测试透明、色彩空间和缓存回收；不引入另一套渲染器。
- 保持原加载缓存、失败占位和网络重试。不要在首页一次预加载所有151个角色。更新实际加载URL的版本标记，避免刷新仍看到旧模型。
- 优先使用项目已支持的GLB/Meshopt链路。不要无故引入Draco/KTX2等新解码依赖；若资源中使用纹理，应自包含且在实际服务的CSP下正常加载。

## 5. 性能与模型结构

精修源文件可以更细，**游戏导出件需要优化**。可以保留高细节源层和单独的游戏导出集合；关闭隐藏构造件、渲染灯光、相机和演示地台的导出。

当前已有自动检查的预算可作为起点，先以实际文件确认：

- 原版高质量总包：每角色少于10,000三角形，总包少于220,000三角形、2.25MiB。
- 原版economy总包：每角色少于4,000三角形，总包少于80,000三角形、1.25MiB。
- Second Wind / Extra Mile / Leaf：现有检查通常要求每件约8,000三角形以内、100,000字节以内、最多9次材质绘制。
- Wurstii：现有文件通常采用顶点色、单材质，每件约155–301KB；它的单件检查预算是320,000字节，不能套用其他包的100KB限制。

这些是现有工程约束，不能靠伪填manifest或删除检查绕过。优先用更好的拓扑、轮廓和共享材质提升质量；如某项改进确需合理调整预算，说明具体角色、视觉收益和实测成本，并保留明确的新上限。不要无依据地给全目录统一翻倍面数，也不要为了旧的字节数字将面部简化回原样。

测量实际游戏中的三角形、draw calls、资源下载量与帧时间，注明设备、视口、人数、画质、动作设置和测量方法。浏览器390px截图不是实体手机性能测试，不能写成“已在手机流畅运行”。

## 6. 执行顺序

1. **盘点**：生成151个角色及额外模块的覆盖清单，保存已有规格，核对素材来源、源工程和加载优先级。
2. **代表样本**：先完成约8个差异明显的角色，覆盖人形服装、动物、软体、长肢、多体组合、硬表面、坐骑和变身。建议从coach、hare、gunk、kraken、copycat、leaf-revolutionary、hog-knight及bite-mark中选择，并补测一个Wurstii。数量可按类型覆盖调整。
3. **样本进入真实游戏**：同时检查近景、总览、同格拥挤、高低画质和动作，先解决材质/骨骼/坐标等共同问题。样本是制作顺序，不是最终交付范围；自检收敛后继续完成其余角色，不要只交8个就结束。
4. **逐包制作**：每个角色按识别特征单独审查，逐包保存与验证。可以共用导出、材质、检查工具，不能用同一个身体模板批量改色代替设计。
5. **全量核对**：角色与资源登记逐项一一对应，确认153个逻辑造型项及现有质量档位均交付。按清单如实标出任何未完成项，不把缺模型藏成原版回退。

如果确实需要我决定视觉方向，展示已完成的具体样本、问题和推荐方案；其他不依赖该决定的工作继续推进。不要反复询问已经明确的“是否覆盖全部角色”。
